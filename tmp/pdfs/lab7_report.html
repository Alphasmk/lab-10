1. Назначение и устройство

Проект продолжает систему управления мероприятиями. Клиент обращается к серверу по HTTP. Сервер хранит площадки, участников, мероприятия и регистрации в двух экземплярах PostgreSQL. После успешной регистрации или отмены сервер публикует событие через сохранённый механизм Pub/Sub.

Сервер создаёт пять учебных узлов с ID 1–5. Доступный узел с наибольшим ID становится лидером. Регистрация и отмена сначала предлагают узлам изменение RegistrationStatus. Большинство фиксировано: три положительных голоса из пяти. Без большинства операция не записывает данные и возвращает HTTP 503.

Последовательность операции

Клиент → сервер → выбор лидера и голосование → запись в PostgreSQL → фиксация решения → Pub/Sub. Если большинства нет, обработка заканчивается до записи.

Модель работает в одном процессе. Состояние узлов хранится в памяти и сбрасывается после перезапуска. Это учебная модель отдельных идей Paxos, Raft и Zab, а не полная реализация протоколов.

3. Узлы, сообщения и выборы

ConsensusNode хранит ID, список соседей, доступность, роль лидера, настройку голоса и последнее принятое значение. Сообщения содержат отправителя, получателя, тип и GUID предложения. Узел проверяет адреса, тип и ID предложения; некорректные сообщения отклоняются и журналируются.

При старте выбирается доступный узел с максимальным ID. Перед выборами прежние роли сбрасываются, поэтому лидер только один; если доступных узлов нет, лидера нет. Heartbeat отправляется каждую секунду. Отсутствие ответа по истечении 250 мс фиксирует отказ. При отказе лидера запускаются повторные выборы; восстановленному узлу передаётся принятое значение COMMIT.

Голосование и обработка ошибок

Лидер предлагает изменение доступным узлам, включая собственный голос. Недоступные узлы не голосуют. Порог большинства всегда 3 из 5. При меньшем количестве YES операция хранилища не вызывается. При ошибке хранилища принятое состояние не меняется. События Pub/Sub публикуются только после успешной записи.

Server/Program.cs:24–25 — создание кластера и периодическая проверка узлов.

Связь с алгоритмами

Роли Leader/Follower и перевыбор связаны с идеями Raft. Большинство показывает понятие кворума из Paxos. Координация лидером распространения согласованного изменения связана с назначением Zab. Полные протоколы не реализуются.
